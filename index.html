PACT problem types, revision -01

Revision -01 of the Internet-Draft draft-laxsharma-pact reports failures as problem details in the format of RFC 9457. Each kind of failure has a type, and each type is identified by an address under https://pact-spec.github.io/problem/. Section 18.5 of that revision says documentation is kept at this prefix. These pages are that documentation.

The draft defines eight types, in its Table 9. The reference implementation of revision -01 uses twenty-two more for failures that table does not cover. Each page says which of the two it is, which section of the draft the response names, and where the recorded run of the implementation shows it.

A program should treat a type as an identifier and compare it as a string. It does not need to fetch the address.

What a response looks like

This is the body of event 26 of the recorded run, sent with status 422 and the media type application/problem+json. The section member carries the number of the section of revision -01 that states the rule.

{
  "type": "https://pact-spec.github.io/problem/assurance-constraint-unsatisfied",
  "title": "assurance constraint unsatisfied",
  "status": 422,
  "detail": "Bond 18.00 is below the minimum 20.00 required for q_min 0.90 at price 180.00 with E 0.00.",
  "section": "7.2",
  "required_bond": "20.00",
  "declared_bond": "18.00",
  "q_min": 0.9,
  "price": "180.00"
}

Recorded: the exchange of the recorded run, or the test vector, that was answered with the type. Not recorded: the implementation returns the type, and neither shows it. Not returned: the implementation lists the type and no request is answered with it.

These identifiers belong to revision -01 of draft-laxsharma-pact, an individual Internet-Draft that later revisions have superseded. Later revisions do not use this prefix.

The implementation described is the reference implementation at tag v0.1.2 of pact-spec/spec.
